# PACT：产品 AI 契约化交付流程

> AI Product Contract  
> 一套面向产品经理、独立开发者和小团队的 AI 辅助产品开发流程：用「契约」替代口头沟通，用「可执行规范」替代传统 UI/UX 出稿，用「接口契约」连接前端原型与后端开发。

## 1. 这是什么

PACT 是一套从产品需求文档到可联调产品原型的标准流程。

它解决的问题是：

- PM 已经用 AI 产出了 PRD、竞品分析、功能清单等文档，但不知道如何进入开发。
- 团队想省去传统 UI/UX 设计稿环节，但又不希望 AI 生成的页面像 Demo、难用、不一致。
- 前端页面、后端接口、数据字段经常对不上，联调成本高。
- AI 写代码时容易自由发挥，缺少页面状态、交互规则、接口边界和验收标准。

PACT 的核心不是「让 AI 直接写页面」，而是：

```text
PRD
→ 页面设计契约
→ API 接口契约
→ Mock 前端原型
→ 后端 API
→ 前后端联调
→ UIUX / 功能验收
```

一句话概括：

> 先让 AI 生成契约，再让 AI 根据契约生成页面和接口。

## 2. 适用场景

PACT 适合以下项目：

| 场景 | 是否适用 |
|---|---|
| MVP 产品从 0 到 1 | 适用 |
| Web 管理后台 | 适用 |
| 微信小程序 / 移动 H5 | 适用 |
| SaaS、CRM、订单、履约、内容工具 | 适用 |
| PM + AI 编程的独立开发模式 | 适用 |
| 需要严肃视觉品牌的大型商业项目 | 可作为开发前置流程，但仍建议专业设计参与 |
| 强视觉营销官网 | 可用，但需要额外品牌与视觉创意流程 |

## 3. 核心原则

### 3.1 省掉设计稿，不省掉设计规则

PACT 可以不要求先画 Figma / Axure / 墨刀原型，但必须保留：

- 页面目标
- 信息架构
- 用户任务
- 主操作与次操作
- 页面状态
- 表单校验
- 响应式规则
- Design Token
- 组件规范
- UIUX 走查标准

### 3.2 前端不直接读 PRD 写页面

PRD 是业务需求，不是前端实现说明。

前端 AI 必须读取：

- 页面设计契约
- Design Token
- 组件规范
- API 接口契约
- 验收清单

### 3.3 后端不猜前端字段

后端接口必须依据 API 契约实现。

每个接口都要明确：

- 请求路径
- 请求方式
- 请求参数
- 返回字段
- 错误码
- 状态流转
- 对应页面
- 对应验收标准

### 3.4 先 Mock，后联调

前端原型先使用 Mock 数据跑通完整交互。

Mock 阶段必须覆盖：

- loading
- empty
- error
- success
- disabled
- 表单校验失败
- 接口异常
- 权限不足

Mock 跑通后，再切换真实 API。

## 4. 推荐项目目录

可以在任意项目根目录使用以下结构：

```text
项目根目录/
├── 01-竞品分析/
├── 02-产品文档/
├── 03-品牌设计/
├── 04-UIUX设计/
├── 05-技术文档/
├── 06-项目编码/
└── 07-其他文档/
```

各目录建议放置内容：

| 目录 | 内容 | 作用 |
|---|---|---|
| `01-竞品分析/` | 竞品拆解、差评分析、替代方案研究 | 给产品定位和界面参考提供依据 |
| `02-产品文档/` | PRD、用户流程、页面清单、验收标准 | 作为需求源 |
| `03-品牌设计/` | 品牌调性、Logo、色彩方向、字体风格、图标风格 | 约束视觉气质 |
| `04-UIUX设计/` | 页面设计契约、Design Token、组件规范、UIUX 走查报告 | 替代传统 UI/UX 出稿的核心目录 |
| `05-技术文档/` | API 契约、openapi.yaml、数据库设计、联调记录 | 约束前后端开发 |
| `06-项目编码/` | frontend、backend、miniapp 等代码 | 实际开发目录 |
| `07-其他文档/` | 决策记录、会议纪要、临时资料 | 项目沉淀 |

## 5. 在项目根目录下怎么使用

PACT 不是单独放在一边看的方法论，而是直接嵌入项目根目录使用。

这里要区分两个目录：

| 类型 | 说明 |
|---|---|
| PACT 规范仓库 | 存放 README、templates、prompts、examples，作为方法和模板来源 |
| 你的业务项目 | 真正开发产品的项目根目录，只需要复制必要模板并放置 `PACT.md` |

业务项目不需要完整复制 PACT 仓库，只需要在项目根目录放一个 `PACT.md`，再按阶段把模板复制到对应目录。

推荐做法：

```text
你的项目/
├── 01-竞品分析/
├── 02-产品文档/
├── 03-品牌设计/
├── 04-UIUX设计/
├── 05-技术文档/
├── 06-项目编码/
├── 07-其他文档/
└── PACT.md
```

其中 `PACT.md` 是项目级流程说明，可以从本仓库 README 摘要复制，也可以只写清楚本项目采用 PACT 的目录约定、阶段门禁和交付标准。

### 5.0 快速开始

PACT 有两种接入方式，**都靠仓库根目录的 `SKILL.md` 自动守门**（初始化 + 阶段纪律 + 硬规则），不需要手动粘贴长提示词。

#### 5.0.1 项目内嵌入（推荐，逐项目隔离）

在业务项目根目录执行：

```bash
git clone git@github.com:genapohub/pact-flow.git .pact
```

克隆后，`SKILL.md` 已经在 `.pact/` 里。打开 coding agent（Claude Code / Codex / Cursor / Trae / Open Design 等），**只要说一句**：

> 用 PACT 初始化本项目，并录入项目背景。

agent 会自动读取 `.pact/SKILL.md`，完成：

1. 创建 7 个标准目录（`01-竞品分析/` … `07-其他文档/`）。
2. 把模板复制到对应位置：根目录 `PACT.md`、`DESIGN.md`、验收清单、页面设计契约、API 接口契约、联调记录（不覆盖已有文件）。
3. 把 `.pact/` 写入 `.gitignore`——规范仓库只在本地引用，不进业务仓库。
4. 读取生成的 `PACT.md`，生成 `07-其他文档/项目背景_v1.0.md` 与 `02-产品文档/项目_PRD_v0.1.md` 骨架，输出就绪报告。

之后每次对话，agent 会先读 `PACT.md` 再工作（守门由 skill 自动执行）。规范更新时 `git -C .pact pull`。

#### 5.0.2 全局技能安装（四端，免逐项目克隆）

把 PACT 作为全局技能装进各 coding 工具，任何项目都能直接触发，无需在每个项目里克隆 `.pact`：

```bash
git clone git@github.com:genapohub/pact-flow.git ~/.workbuddy/skills/pact-flow    # WorkBuddy
git clone git@github.com:genapohub/pact-flow.git ~/.codex/skills/pact-flow         # Codex
git clone git@github.com:genapohub/pact-flow.git ~/.cursor/skills-cursor/pact-flow # Cursor
```

> 注意：ZCode 端你已卸载、不再同步；如需重新启用，补齐上面同款命令（目标目录 `~/.zcode/skills/pact-flow`）即可。全局安装后，skill 初始化模板来源回退为「本 skill 同级 `templates/`」（见 SKILL.md 第 1 节）。更新用 `git -C <目录> pull --ff-only`。

#### 5.0.3 手动降级路径（工具不支持 SKILL.md 时）

如果所用工具不识别 `SKILL.md` 自动触发，回到 5.1 手动创建目录 + 5.2 启动语，或把 `.pact/prompts/项目初始化提示词.md` 整段粘贴发送（替换尖括号里的项目背景），效果等价。

已有项目也可以只放一个 `PACT.md`（见 5.1 手动流程），效果等价。

### 5.1 第一次初始化项目

新建项目时，先创建目录：

```text
mkdir 01-竞品分析 02-产品文档 03-品牌设计 04-UIUX设计 05-技术文档 06-项目编码 07-其他文档
```

然后把本仓库的模板复制进去：

```text
templates/PACT项目说明模板.md       → PACT.md
templates/DESIGN.md模板.md          → DESIGN.md
templates/页面设计契约模板.md      → 04-UIUX设计/页面设计契约_v1.0.md
templates/API接口契约模板.md       → 05-技术文档/API接口契约_v1.0.md
templates/验收清单模板.md          → 02-产品文档/验收清单_v1.0.md
templates/联调记录模板.md          → 05-技术文档/联调记录.md
```

其中 `PACT.md` 是最重要的项目级说明。

**文件命名约定（单模块 / 多模块）**

同一项目内只能选一种，不能混用：

| 项目类型 | 命名方式 | 示例 |
|---|---|---|
| 单模块项目（MVP、只有一个业务模块） | 通用名，不加前缀 | `02-产品文档/页面清单_v1.0.md`、`04-UIUX设计/页面设计契约_v1.0.md` |
| 多模块项目（订单管理、客户管理…并存） | 加 `<模块名>_` 前缀 | `02-产品文档/订单管理_页面清单_v1.0.md`、`04-UIUX设计/订单管理_页面设计契约_v1.0.md` |

- 规范文件不参与前缀：`PACT.md`、`DESIGN.md`、`05-技术文档/联调记录.md` 固定位置，始终同名。
- 初始化生成的 `项目_PRD_v0.1.md` 是项目级总纲：单模块项目直接升级为 `项目_PRD_v1.0.md`；多模块项目另建 `模块名_PRD_v1.0.md`，总纲保留。
- 版本后缀固定 `_v1.0` 格式，改版递增，不出现 `最终版` 之类命名。

每次让 AI 参与项目开发前，先要求它读取：

```text
PACT.md
```

它的作用类似轻量版项目宪法：告诉 AI 这个项目的目录怎么用、哪些文件是需求源、哪些文件是契约、代码能写到哪里、变更要先改哪里。

### 5.2 给 AI 的项目根目录启动语

在任何 AI 编程工具里开始一个项目任务时，可以先发：

```text
请先读取项目根目录下的 PACT.md。
本项目采用 PACT：产品 AI 契约化交付流程。
你需要先确认当前任务属于哪个阶段，再读取对应目录文件。
在没有更新需求契约、UIUX 契约或 API 契约前，不要直接修改代码。
```

### 5.3 每个目录在开发中的读写规则

| 目录 | AI 什么时候读取 | AI 什么时候写入 | 关键约束 |
|---|---|---|---|
| `01-竞品分析/` | 需求结构化、UIUX 定方向时读取 | 竞品调研阶段写入 | 不直接决定功能，只提供参考 |
| `02-产品文档/` | 所有阶段都要读取 | PRD、页面清单、验收清单阶段写入 | 是需求源，开发中不能随意改 |
| `03-品牌设计/` | 生成 UIUX 契约和前端页面前读取 | 品牌定位、颜色、字体、图标规则阶段写入 | 约束视觉气质 |
| `04-UIUX设计/` | 前端生成前必须读取 | 页面设计契约、Design Token、走查报告写入 | 是省掉设计稿后的核心约束 |
| `05-技术文档/` | 前后端开发和联调前必须读取 | API 契约、openapi、数据库、联调记录写入 | 是前后端接口契约 |
| `06-项目编码/` | 开发、调试、测试时读取 | 前端、后端、小程序代码写入 | 代码只能依据契约实现 |
| `07-其他文档/` | 交付和复盘时读取 | 决策记录、交付说明、临时资料写入 | 不承载核心开发契约 |

### 5.4 一次真实开发任务怎么跑

假设你要开发「订单管理」模块，不要直接对 AI 说“帮我写订单页面”。

> 下面按多模块项目命名，契约文件带 `订单管理_` 前缀；单模块项目可省略前缀（见 5.1 文件命名约定）。

应该按下面顺序发任务：

```text
任务 1：请读取 02-产品文档/订单管理_PRD_v1.0.md，
生成 02-产品文档/订单管理_页面清单_v1.0.md 和 02-产品文档/订单管理_验收清单_v1.0.md。

任务 2：请读取 02-产品文档/、03-品牌设计/，
生成 04-UIUX设计/订单管理_页面设计契约_v1.0.md 和 04-UIUX设计/design-tokens.json。

任务 3：请读取 04-UIUX设计/订单管理_页面设计契约_v1.0.md，
生成 05-技术文档/订单管理_API接口契约_v1.0.md 和 05-技术文档/openapi.yaml。

任务 4：请读取 02-产品文档/、04-UIUX设计/、05-技术文档/，
在 06-项目编码/frontend/ 生成订单管理前端页面，先接 Mock 数据。

任务 5：请读取 05-技术文档/，
在 06-项目编码/backend/ 实现订单管理 API，并提供 /healthz。

任务 6：请读取 02-产品文档/验收清单、04-UIUX设计/页面设计契约、05-技术文档/API接口契约，
完成前后端联调，并把问题记录到 05-技术文档/联调记录.md。
```

### 5.5 项目级门禁

每个阶段完成后，都要判断能不能进入下一阶段：

| 阶段 | 进入下一阶段前必须满足 |
|---|---|
| PRD → 页面设计契约 | 页面清单、用户流程、验收清单已明确 |
| 页面设计契约 → API 契约 | 页面状态、表单、列表、弹窗、响应式规则已明确 |
| API 契约 → 前端 Mock | 每个页面需要的数据都有接口或 Mock 数据来源 |
| 前端 Mock → 后端开发 | 前端核心流程已用 Mock 跑通 |
| 后端开发 → 联调 | `/healthz` 可用，核心 API 返回格式统一 |
| 联调 → 交付 | 验收清单通过，UIUX 走查没有阻断问题 |

### 5.6 变更怎么处理

开发中发现需求要改，不要直接改代码。

按影响范围处理：

| 变更类型 | 处理方式 |
|---|---|
| 文案、按钮名称、小字段校验 | 更新 `04-UIUX设计/页面设计契约_v1.0.md`，再改前端 |
| 新增页面状态、表单字段、列表筛选 | 更新 `04-UIUX设计/` 和 `05-技术文档/`，再改代码 |
| 新增接口、修改字段结构 | 先更新 `05-技术文档/API接口契约_v1.0.md` 和 `openapi.yaml` |
| 核心流程变化 | 回到 `02-产品文档/` 更新 PRD、页面清单和验收清单 |

原则：

> 代码变更必须追溯到契约变更，不能只改代码不改文档。

## 6. PACT 六阶段流程

### Phase 1：需求结构化

输入：

- PRD
- 竞品分析
- 用户场景
- 业务流程

输出：

```text
02-产品文档/
├── 项目_PRD_v1.0.md
├── 页面清单_v1.0.md
├── 用户流程_v1.0.md
└── 验收清单_v1.0.md
```

验收标准：

- 核心用户是谁清楚。
- 用户要完成的任务清楚。
- MVP 做什么、不做什么清楚。
- 每个页面服务哪个业务目标清楚。

### Phase 2：页面设计契约

输入：

- PRD
- 页面清单
- 用户流程
- 品牌设计方向
- UIUX设计
- 高保真UI原型

输出：

```text
04-UIUX设计/
├── 页面设计契约_v1.0.md
├── design-tokens.json
├── 组件规范_v1.0.md
└── 小程序交互规范_v1.0.md
```

页面设计契约至少包含：

| 模块 | 说明 |
|---|---|
| 页面目标 | 这个页面帮助用户完成什么任务 |
| 用户路径 | 用户从哪里来、完成后到哪里去 |
| 信息优先级 | 首屏必须看到什么，哪些可以弱化 |
| 主操作 | 页面最重要的动作 |
| 次操作 | 辅助动作、取消动作、返回动作 |
| 危险操作 | 删除、取消、退款、关闭等需要确认的动作 |
| 页面状态 | loading、empty、error、success、disabled |
| 表单规则 | 字段、校验、错误提示、提交反馈 |
| 列表规则 | 搜索、筛选、排序、分页、空数据 |
| 弹窗规则 | 触发条件、确认动作、取消动作 |
| 响应式规则 | PC、移动端、小程序分别怎么布局 |
| 无障碍规则 | 对比度、触控区、焦点态、错误提示 |

### Phase 3：API 接口契约

输入：

- 页面设计契约
- 页面数据需求
- 业务状态流转

输出：

```text
05-技术文档/
├── API接口契约_v1.0.md
├── openapi.yaml
├── 数据库设计_v1.0.md
└── 错误码规范_v1.0.md
```

推荐统一响应格式：

```json
{
  "code": 0,
  "data": {},
  "message": "success"
}
```

每个接口必须包含：

| 字段 | 说明 |
|---|---|
| 接口名称 | 例如：创建订单 |
| 请求方式 | GET / POST / PUT / DELETE |
| 请求路径 | 例如：`/api/orders` |
| 请求参数 | query、path、body |
| 返回字段 | 页面需要展示的数据 |
| 错误码 | 参数错误、权限不足、状态冲突等 |
| 对应页面 | 该接口服务哪些页面 |
| 验收标准 | 如何判断接口可用 |

### Phase 4：前端 Mock 原型

输入：

- 页面设计契约
- Design Token
- 组件规范
- API 接口契约

输出：

```text
06-项目编码/
└── frontend/
```

前端实现要求：

- 页面可真实点击。
- 表单可真实校验。
- 列表可搜索、筛选、分页。
- 弹窗可打开、确认、关闭。
- 所有页面状态齐全。
- 所有视觉样式来自 Design Token。
- 图标使用统一图标库，不使用 emoji 作为功能图标。
- 不使用 Lorem ipsum 等无业务意义占位文案。

### Phase 5：后端 API 实现

输入：

- API 接口契约
- openapi.yaml
- 数据库设计
- 验收清单

输出：

```text

└── backend/
```

本地开发建议：

- 先实现健康检查接口。
- 再实现认证、权限、业务接口。

- 字段命名与 API 契约一致。

4. 先跑核心成功流程。
5. 再跑异常、空数据、权限、边界场景。
6. 最后做 UIUX 走查和功能验收。

## 7. UIUX 走查清单

### 7.1 UX 走查

- 页面目标是否一眼明确。
- 主操作是否突出。
- 次操作是否不会干扰主操作。
- 用户完成任务的步骤是否足够少。
- 错误提示是否说明了发生什么、为什么、怎么办。
- 空状态是否告诉用户下一步可以做什么。
- 表单是否只收集必要字段。
- 危险操作是否有二次确认。
- 页面跳转是否符合用户预期。

### 7.2 UI 走查

- 字体层级是否清楚。
- 间距是否统一。
- 主色、辅助色、警示色是否来自 Token。
- 按钮样式是否区分主次。
- 表格是否适合高频扫描和操作。
- 小程序触控区是否不小于 44px。
- 图标风格是否统一。
- 移动端是否没有横向溢出。
- 页面不像通用 AI 模板。

### 7.3 状态走查

每个核心页面都要检查：

- default
- loading
- empty
- error
- success
- disabled
- hover
- focus
- active

## 8. 给 AI 的提示词模板

### 8.1 从 PRD 生成页面设计契约

```text
你是资深产品经理和 UIUX 设计师。

请根据以下 PRD 输出页面设计契约，不要写代码。

输出内容必须包含：
1. 页面清单
2. 每个页面的页面目标
3. 用户进入和离开路径
4. 信息优先级
5. 主操作、次操作、危险操作
6. loading / empty / error / success / disabled 状态
7. 表单字段、校验规则、错误提示
8. 列表搜索、筛选、排序、分页规则
9. PC / 移动端 / 小程序适配规则
10. Design Token 建议
11. 组件清单
12. 验收标准

要求：
- 不要生成营销页风格

- 不要使用空泛描述
- 所有页面都要面向真实业务操作
```

### 8.2 从页面设计契约生成前端原型

```text
你是高级前端工程师。

请严格根据页面设计契约、Design Token、组件规范和 API 接口契约生成可运行前端页面。

要求：
1. 先使用 Mock 数据完成交互
2. 实现 loading、empty、error、success、disabled 状态
3. 表单必须有校验和错误提示
4. 列表必须支持搜索、筛选和分页
5. 弹窗必须支持确认、取消和关闭
6. 所有颜色、字体、间距、圆角、阴影来自 Design Token
7. 不使用 emoji 作为功能图标
8. 不使用 Lorem ipsum
9. 代码结构要方便后续接入真实 API
```

### 8.3 从页面需求生成 API 契约

```text
你是高级后端架构师。

请根据页面设计契约和页面数据需求，输出 API 接口契约。

每个接口必须包含：
1. 接口名称
2. 请求方式
3. 请求路径
4. 请求参数
5. 返回字段
6. 错误码
7. 对应页面
8. 对应业务状态
9. 验收标准
10. 示例请求和示例响应

要求：
- 字段命名保持一致
- 不要让前端猜字段
- 不要省略异常场景
- 接口必须支持页面的全部状态展示
```

```text
你是 高级UIUX 走查负责人。

请根据页面设计契约和当前前端实现进行走查。

检查维度：

6. 表单校验和错误提示是否可理解

8. Design Token 是否被正确使用
9. 是否存在 AI 模板味

- 阻断问题
```

## 10. 仓库文件说明

如果你直接使用本仓库，建议按下面方式使用：

```text
SKILL.md      → 核心：coding agent 自动识别并守门（初始化 + 阶段纪律 + 硬规则）。克隆即生效，无需粘贴提示词
templates/    → 初始化时复制到项目对应目录后填写
prompts/      → AI 工具提示词库（手动降级路径 / 参考入口在 prompts/项目初始化提示词.md）
examples/     → 参考示例，不要直接当业务模板套用
```

> 接入优先级：克隆 `.pact`（或全局装技能）→ `SKILL.md` 自动守门 → 无需手动粘贴提示词。只有当工具不支持 `SKILL.md` 时才回到 `prompts/` 手动路径。

## 11. Definition of Done

一个使用 PACT 的项目，至少满足以下条件才算进入可交付状态：

- PRD 已明确 MVP 范围。
- 每个核心页面都有页面设计契约。
- 每个核心页面都有完整状态设计。
- Design Token 已定义并被前端使用。
- API 接口契约覆盖页面数据需求。
- 前端 Mock 流程已跑通。
- 后端健康检查可用。
- 前端已切换真实 API 并跑通核心流程。
- UIUX 走查没有阻断问题。
- 验收清单已逐项确认。

## 12. PACT 不解决什么

PACT 不替代：

- 商业模式判断
- 深度用户研究
- 高级品牌创意
- 复杂动效设计
- 大规模工程治理
- 安全合规审计

PACT 解决的是：

> 在 PM 和 AI 工具协作开发产品时，如何把需求、页面、接口、代码和验收连接成一个可执行闭环。

## 13. 如何维护 pact-flow（本仓库自身）

本仓库既是**三端全局技能**（装进 coding agent 的 skills 目录，任何项目可触发），也是**项目内嵌快照**（业务项目 `git clone ... .pact`）。维护时记住下面四条链路。

### 13.1 四个位置

| 角色 | 位置 | 说明 |
|---|---|---|
| 源仓库（唯一编辑入口） | 你本地克隆 `genapohub/pact-flow` 的仓库根目录（例如 `~/Downloads/WorkBuddy/pact-flow/`） | **只在这里改文件** |
| 远程仓库 | `git@github.com:genapohub/pact-flow.git` | SSH，唯一中转 |
| 三端全局副本 | `~/.workbuddy/skills/pact-flow/`、`~/.codex/skills/pact-flow/`、`~/.cursor/skills-cursor/pact-flow/` | coding agent 全局触发用 |
| 业务项目内嵌副本 | 各项目根 `.pact/` | 独立快照，**不**随三端自动更新 |

### 13.2 日常维护（改模板 / 提示词 / SKILL.md）

```bash
# 1. 在源仓库修改（唯一入口），然后提交推送
git -C <源仓库> add -A
git -C <源仓库> commit -m "说明改了什么"
git -C <源仓库> push

# 2. 三端全局副本各自同步
for d in ~/.workbuddy/skills/pact-flow ~/.codex/skills/pact-flow ~/.cursor/skills-cursor/pact-flow; do
  git -C "$d" pull --ff-only
done

# 3. 业务项目内嵌快照按需更新
git -C <你的项目>/.pact pull
```

> 用 `pull --ff-only` 而非 `pull`：避免下游副本出现本地提交造成反向漂移或合并冲突。

### 13.3 加新能力

- **只改 `SKILL.md` 或 `prompts/`，不加脚本** —— PACT 的执行主体是 agent，不是脚本（历史 `init.sh` 已因此删除）。
- 新模板放 `templates/`，新提示词放 `prompts/`，三端 clone 会自动带走。
- 能力有实质变化时，同步递增 `SKILL.md` frontmatter 的 `version` 字段（当前 `1.0.0`）。

### 13.4 已知坑

- **remote 必须是 SSH**：HTTPS remote 在无凭证环境下 `pull` 会静默失败。
- **源仓库改之前先 `git pull`**：防止源落后于 GitHub 导致下游反向漂移。
- **zsh 循环目录用数组**：`for d in ${arr[@]}`，不要用 `$VAR` 靠空格分割。
- **目录名相近**（`skills` / `skills-cursor`）：巡检输出用完整路径区分三端。
- 本仓库**没有 `memory/` 目录**，三端 `pull` 不会因运行记忆文件冲突。

### 13.5 不要做的事

- 不要在 `~/.workbuddy/skills/pact-flow/` 或业务项目 `.pact/` 里直接改文件后回推（反向漂移）。
- 不要随意改 GitHub 仓库名（改名后旧 URL 仅短期重定向，需同步更新所有 remote）。
- 不要把新能力写成 shell 脚本。
